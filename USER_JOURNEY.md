# Monovella — Prototype Demonstration Scenarios

**Purpose:** answer `../../TODO.md`'s open "Realistic demonstration scenario" item — the prototype's fixtures and automated tests are structurally correct (`mise run check` passes) but have never been walked as one coherent story a founder, advisor, or ACE reviewer would actually watch. This document is that walkthrough script. Each scenario is a manual click-through against the running dev server (`mise run dev`); `mise run test` already proves the fixture mechanics, and this proves the *demonstration* holds together end to end, surfacing what only a human notices (tone, pacing, a number that doesn't add up, a state that's technically correct but reads badly on screen).

**This document is also the test suite's registry.** `tests/e2e/journeys.ts` parses the scenario headings and checklist bullets below rather than copying them, so the two cannot drift; every end-to-end test declares which bullet it walks, and `mise run e2e` prints the coverage per scenario and fails if it goes backwards. Path ids are positional — `C6` is the sixth bullet of Scenario C — so **inserting or removing a bullet renumbers every path after it in that scenario**. A pinned count in `tests/unit/journey-registry.test.ts` turns that into a failing test rather than a silently re-pointed claim: when it fails, re-check the claims in that scenario's specs before updating the count. Walking a scenario by hand remains the point of this file; the automated coverage is a floor under it, not a replacement for it.

**Evidence discipline:** Scenario C's trigger is real — it restates the sourced interview in `../../Business_Docs/Customer_Journey.md` (Cherish, a Lagos salaried professional's gynaecology episode), walked using the prototype's actual demo account (`pat_amara` / Amara Okonkwo) because Cherish herself was never a Monovella user. Every other scenario is a constructed test persona built to stress a specific risk area already named in `../../TODO.md` — prototype test data, not customer evidence, and never to be cited as demand or validation.

**How to log a gap:** when a step fails, reads badly, or a number/state looks wrong, do not edit this file. Add it to `../../TODO.md` under a new dated entry (or the existing "Realistic demonstration scenario" item) with the scenario/step reference, then fix it and check the step here.

## Mechanics — how to actually drive this script

- **Start at `/tour`.** Each of the five tiles ("Pick a seat") signs you straight into that surface — patient, expert, back-office, pharmacy, lab — with no password. This is the intended entry point for this document; don't navigate to deep routes cold.
- **Reset before a first walk of any scenario:** the prototype bar's reset control restores the shipped fixtures. State otherwise persists in `sessionStorage`, so an earlier walkthrough's mutations (an accepted request, a filed complaint) carry into the next one.
- **Declared states live in the prototype bar**, not on the page — it's the dropdown at the foot of the window. Use it for any state a normal action can't easily reach (a specific 409, a rate limit, `EXPIRING_SOON`).
- **The expert seat is one of exactly five fixed identities, not "any expert in the directory."** `/app/expert` puts you in Amara's own switchable expert context — a verified dermatologist, fixture id `exp_adeyemi` — by default. Expert Home's (X4) state-switcher dropdown can additionally select "Seat: Nurse," "Seat: Pharmacist," "Seat: Lab Scientist," or "Seat: Physiotherapist," each pinned to its own fixture id. **There is no way to become a specific named Doctor other than `exp_adeyemi`** (not Dr. Eze, not any other directory listing) — those experts exist only as counterparties you interact with from the *patient* side (booking them, receiving their chat replies, seeing their prescriptions), never as a seat you sit in yourself.
- **What this means for "whose journey are we capturing":** a scenario walking a *patient's* journey should use whichever directory expert the real story calls for (Dr. Eze for a gynaecology concern) and treat that expert's own actions — accepting, replying, prescribing — as fixture state to observe, not perform. A scenario walking the *expert's* journey performs those same actions for real, but only `exp_adeyemi` (or one of the four named alternates) can be that expert. Don't collapse the two into one scenario just because a single demo account technically can play both parts — that produces a workaround, not a captured user journey.
- **Self-booking is not allowed — an expert cannot treat themselves.** Amara's own patient identity (`pat_amara`) must never be the counterparty when testing `exp_adeyemi`'s own live journey; the fixtures already model the correct pairing instead — `con_106` is a real consultation between `exp_adeyemi` and Tobi (`pat_tobi`), her dependant, a distinct patient identity. For any live two-party test of the expert's own actions (accept, real-time chat, the call sequence, prescribing), switch the patient context to a dependant first, then use two tabs of the same account: one in that dependant's Patient context, one switched to Expert (`exp_adeyemi`). Never construct a fresh booking from Amara's own patient identity to her own expert identity — that pairing should be attempted at most once, deliberately, to confirm it's correctly refused (see Scenario P).
- **Patient auth screens (P5–P10) aren't reachable cold.** Arriving via `/tour` or `/app` signs you straight in, so to walk Scenario B's patient half, sign out first from Account Settings (P58) — that's what actually flips the session back to signed-out and routes you to Welcome/Sign In.

## B. Authentication, recovery and session management — patient, staff and provider

**Persona:** three separate returning users, each locked out in a different way: a patient who forgot her PIN, a staff member with an expired password, a provider who lost portal access. **Seats:** Patient, Back-Office staff, Provider Portal. **Entry:** each surface's own sign-in route.

- [ ] Sign In (P5) with the wrong PIN twice, then the correct PIN on a third attempt — the near-lockout warning appears before an actual lockout blocks the legitimate try
- [ ] Trigger the real lockout on a fresh attempt count and confirm the copy states what to do next (recovery), not just "try again"
- [ ] Recover Account: Start (P6) → Email Verification (P7) using a previously-registered recovery email — completes to a working session
- [ ] Recover Account: Start (P6) → NIN Verification (P8) as the alternate path on an account with no recovery email
- [ ] Recover Account: Manual Support (P9) — the last-resort path when neither automated method applies; produces a trackable case, not a dead end (cross-check Scenario J's support pattern)
- [ ] Set New Phone & PIN (P10) completes recovery and returns a fresh signed-in session
- [ ] OTP expiry and resend cooldown are both reachable by waiting, not just declared in the prototype-bar state list
- [ ] Reuse an already-consumed recovery link — fails closed with a clear reason, never silently reopens recovery
- [ ] Enrol two-factor authentication (P59c): enter one invalid code, then the correct one; generate recovery codes and confirm one single-use code actually works once and fails the second time
- [ ] Simulate biometric unavailable, then cancelled, on Biometric Unlock (P59b) — both fall back gracefully to PIN
- [ ] Device Sessions (P59): revoke one other device, then use "sign out everywhere" — confirm what happens to the *current* device matches what the copy promises (ended vs. kept)

**Staff (`/console/sign-in`):**
- [ ] Staff Sign In (B1) on a first-login account → Forced Password Change (B2) → lands on Console Home (B6), not back at sign-in
- [ ] Forgot Password (B3) → Reset Password (B4) as a separate attempt; reuse the same reset link a second time and confirm it's refused

**Provider — Pharmacy and Lab (`/pharmacy/sign-in`, `/lab/sign-in`):**

- [ ] A provider under an active standing suspension (from Scenario N) can still sign in but sees the standing notice (V12) immediately, not a normal home screen

**Cross-cutting:**
- [ ] Confirm Terms/Privacy/Cookies are reachable from at least one pre-acceptance point on each surface without losing entered progress, and Back/decline never records consent

- [ ] Telemedicine Consent (P41) is readable in under 30 seconds, not a wall of legal text
- [ ] Checkout (card and, separately, transfer) reaches a verified receipt (P48) with no duplicate charge on refresh
- [ ] Booking Status (P40) shows a genuinely positive countdown to expert response, not an already-expired deadline

## F. Safety-first — emergency language must never route to booking

**Persona:** any signed-in patient. **Seats:** Patient. **Entry:** Tell Us What's Going On (P35), both typed and voice.

- [ ] Type an unambiguous emergency phrase into P35 — result interrupts booking with emergency guidance, never offers a specialist match
- [ ] Speak the same phrase (voice intake) — transcript is shown back, confirmed, then classified; emergency detection runs on the *confirmed* text, not the raw guess
- [ ] Try an ambiguous phrase, then a follow-up message that clarifies it's serious — the change in urgency is caught, not locked to the first read
- [ ] Confirm the rate limit on specialty matching never blocks an emergency phrase — a throttled request must still interrupt with guidance, never fail silently
- [ ] Test one spelling/punctuation variant (e.g. missing apostrophe, all lowercase) to confirm detection isn't brittle to exact phrasing

**Watch for:** this is a Critical/patient-safety path — any silent fallthrough to normal specialty matching is a blocker, not a UX nit.

## H. Fulfilment friction, including the no-Monovella-provider fallback

**Persona:** Amara with an active prescription and an active lab order. **Seats:** Patient + Pharmacy + Lab.

- [ ] Send a prescription to a pharmacy that declines/times out — Pharmacy Request Status (P46c) reflects it, and Amara can reselect another pharmacy without creating a duplicate open request

## J. Self-service support, refunds and complaints

**Watch for:** these are the flows that generate support load in real operation — if any of them dead-ends at a toast instead of a trackable case, that's exactly the gap `ops-team` would need closed before launch.
